# Final verification and updating a robot

Framework contract 1.2 separates `setup(ctx)` (once), `process(ctx, inputs)` (per row), `finalize(ctx)` (once after all selected rows succeed), and `teardown(ctx)` (unconditional cleanup after setup was attempted). The framework owns iteration. Final verification is skipped for empty queues, cancellation, failed/rejected rows, and early stops. If final verification fails, the run fails while successful row attempts and their completed queue states are preserved. Do not replay those rows just to retry final verification.

In the specification form allocate every step exactly once across setup, per-row and final checks. Mapped Fill/Select steps require per-row execution. A final Read text step uses `ctx.extract_text` in `finalize`; its outputs are saved as `RobotRun.outputs` and displayed in progress and robot history. Existing row outputs remain separate. Migration `execution.0010_robotrun_outputs` is additive.

For RPA Challenge: Start is setup, seven fills and Submit are per-row, Congratulations is a final check. Set the run limit to all ten required inputs; testing only a subset cannot produce the final challenge screen. `ctx.read_value(id)` reads an actual form value. DOM `read_text` is not an input-value or submission-success check. Where a captured status has changing round text, snapshot its text before Submit and use `ctx.wait_for_progress(status_id, previous_text, completion_id)` afterward. This bounded read-only wait requires changed visible status text or a unique visible completion target; it never resubmits. A captured selector must identify that status across rounds. This is a configured business postcondition, not an automatic proof that every website submission succeeded.

On the Muse build page choose **Update specification for a new robot version (no API call)** to copy decisions onto current project/framework context. This creates an unconfirmed session; it does not alter previous confirmations, versions, runs, or queue states. Review the phase allocation and assumptions, save local decisions, then confirm the agreed specification. Paid generation is a separate explicit action and creates the next version. Source review and launch remain separate explicit actions too.

Contract changes intentionally require fresh confirmation. No automatic API call, robot launch, retry, dependency installation, or old source rewrite occurs.

Muse capability warnings can be corrected locally: describe the supported replacement under **Resolution of Muse capability warnings**, and explicitly confirm that outstanding questions are resolved. Saving records this decision in the frozen specification; it does not grant new capabilities. Local target/mapping/phase validation and generated-code validation still apply. This avoids requiring another paid review merely to correct a model warning such as an incorrectly inferred request for fixed sleeps.
