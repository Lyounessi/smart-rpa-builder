# Smart RPA framework contract 1.2

Generate one subclass of robot_framework.base.BaseRobot; do not override execute.
setup(ctx) prepares/login once. process(ctx, inputs) handles one validated DB row.
finalize(ctx) verifies the overall result once, only after all selected rows succeed.
It runs before teardown, with no current row or inputs. Empty, interrupted, or failed
row processing does not run finalize. Its failure fails the run but preserves completed rows.
teardown(ctx) tolerates partially initialized state. The framework owns browser,
recording, cancellation, queue claims, results and resource cleanup.

Use ctx.navigate(application_id), ctx.fill(element_id, value), ctx.click(element_id),
ctx.select_option(element_id, value), ctx.read_text(element_id), and
ctx.assert_visible(element_id). IDs come from the project; do not invent IDs or
selectors. ctx.read_value(element_id) reads an input/textarea/select value; read_text
reads DOM text and must not be used to check entered or cleared input values.
Use inputs[configured_key] for values. No Django queries or raw
Playwright objects in business code. All actions have bounded waits. Do not use
fixed sleeps, automatic retries, pip, shell/filesystem tools or external clients.

Use with ctx.step('fixed_step_id') for named progress and ctx.checkpoint() for
cooperative cancellation. ctx.secrets.get('SECRET_REFERENCE') resolves secrets at
runtime. Never embed credentials, input values, or provider diagnostics in logs.

Returning from process means explicit success has been verified. Raise
BusinessRejection for known business rejection; technical failures produce ERROR.
Outcomes OK/NOK/ERROR differ from run completed/failed/cancelled. Technical errors
stop by default. recover(ctx, outcome) must restore a known state and return True
before continuation; default False. Do not retry submissions or entire rows.

After verified business success, ctx.business_completed() saves a durable
checkpoint before optional notifications. A notification error must not repeat
the business operation. For email declare EmailStep specifications in email_steps
and use ctx.email.send_step(spec, inputs). Only {{input_key}} substitution is
supported. Email uses an injected adapter; only a fake adapter exists currently.
No real email, OAuth, desktop automation, OCR, tabs/iframes, scheduling or arbitrary
tools are supported. Flag unsupported requests instead of inventing capabilities.

Use confirmed specification decisions for setup/per-row/finalization behavior, success tests
and failure policies. Do not silently change explicit targets, input mappings or
execution settings. If blocking questions or contradictions are identified,
request clarification before generating code. Detection is not guaranteed.

Generated code is a draft for static validation and review, never automatic
execution. Do not import, execute or activate generated source during generation.

For a read_text workflow step call ctx.extract_text(element_id, output_key) inside
process or finalize according to the confirmed step allocation, inside its named
ctx.step block. Use the exact configured captured ID and
output_key. This reads browser text and saves it separately from inputs, once per
output name per row. Values are plain strings, limited to 16 KB each and 64 KB per
row. No arbitrary expressions, transformations, database writes or output schema
invention are needed. A plain read_text call does not save a result. Check success
explicitly before returning or calling business_completed. Outputs are attached
to each row attempt (including partial failed attempts); they reset between rows.
Business-completion checkpoints preserve collected outputs if notifications fail.
Finalize extraction is saved in run outputs, with the same size limits, separately
from row outputs. Do not read a final congratulations message inside process.
Do not treat mere visibility or input inner text as proof a submission succeeded.
For a confirmed text-based progress signal, save previous = ctx.read_text(status_id)
before Submit, then call ctx.wait_for_progress(status_id, previous, completion_id)
after Submit. This bounded wait succeeds when the unique visible status text changes
to nonempty text OR the unique final completion target becomes visible. It does not
click, retry, submit, or save page text in logs. Only use confirmed captured IDs;
the status selector must remain meaningful as rounds change. If no appropriate
status target exists, request clarification rather than inventing one.
